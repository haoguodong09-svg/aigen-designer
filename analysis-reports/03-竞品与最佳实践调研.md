## 0. 现状锚点（epic-designer 仓库，便于后文对照）

探查 `packages/ui-kit/panel-ui/src/rightSidebars/event/event.vue` 与 `AigenActionEditorItem.vue`，当前实现：

- 事件面板按"组件事件 + 生命周期"两组展示，编辑 schema 的 `on` 属性；每个事件下是**动作列表**（可拖拽排序、增删）。
- 动作类型三种：`component`（调用目标组件方法，展示为"组件 label + 方法名"）、`custom`（自定义函数）、`public`（公共函数）。
- 生命周期事件**直接使用 Vue 语义**：`vnodeMounted`（挂载完成-本组件）、`vnodeUpdated`、`vnodeBeforeMount`、`vnodeErrorCaptured` 等 8 个。
- 动作配置走弹窗（组件树/方法列表/参数表单），目标组件通过 `componentId` 引用（`findSchemaById` 找 label 展示）。
- 已具备的底层能力：`find(id).getVal()` 组件方法调用、`publicMethods.fetchData` 公共函数（examples 中可见）。

**结论：底层是"事件-动作"范式，骨架合理，痛点在表达层**——生命周期用框架术语、动作配置器是开发式表单、缺少业务化"规则"中间层、目标组件选择不直观。

## A. 各产品"多元素绑定交互"核心模式

### A1. 百度 amis —— 事件-动作（onEvent），动作生态最完整

**官方文档（已抓取 event-action.md 全文结构）**。核心范式：**每个渲染器组件声明自己的"事件表"（渲染器事件，如 `change`/`click`/`submitSuccess`），通过 `onEvent: { 事件: { actions: [...] } }` 绑定响应动作**。编辑器交互形态为**右侧属性面板中配置 onEvent**（amis 生态 AI 速搭文档有「事件交互」章节，面板式而非连线式，正文细节未抓到）。

动作分四类（这是 amis 最值得抄的能力矩阵）：

- **通用动作**：发送 http 请求（ajax）、弹窗/抽屉/确认框、toast、页面跳转、浏览器回退/刷新、复制、打印、发送邮件、更新事件上下文数据、等待。
- **组件动作**：更新指定组件数据（setValue 语义）、刷新组件请求、修改组件状态（显示/隐藏、启用/禁用、静态展示/编辑态）、**执行目标组件的专有动作**（如表单提交）。
- **广播动作**：派发自定义事件 `eventName`，其他组件监听该事件各自响应——**解耦"一因多果"**。
- **自定义动作**：JS 脚本片段，且支持在 JS 内继续执行动作。
- 另有**逻辑编排**：条件、循环、排他（switch）、并行；**动作间数据传递**（前一动作输出可被后一动作引用）；**干预动作执行**（阻止默认行为、停止后续动作、忽略报错继续）；**运行日志**（浏览器 console 打印每个动作的参数与结果，可调试）。

目标元素定位：动作参数中通过 `componentId` 引用组件（组件状态/更新组件数据动作需选组件）；读取值用表达式 `${event.data}`、`${__rendererData}`（组件当前数据域）。

**可学之处**：① 事件表由组件声明、按事件组织动作列表；② 动作=预设动作类型+目标组件+参数 的三段式，覆盖 90% 场景；③ 广播机制解耦复杂联动；④ 运行日志降低调试成本；⑤ 动作条件化与逻辑编排作为"进阶层"存在，不吓唬初级用户。

### A2. Formily / Designable —— 声明式 Schema 联动（x-reactions）

**核心范式：联动写在 schema 上，而不是写在事件里**。字段通过 `x-reactions` 声明 `dependencies`（依赖的字段路径），`fulfill.state` 控制目标状态（`visible`/`disabled`/`value`/`display`），`fulfill.schema` 甚至可改字段的整个 schema（如换 label、换组件）；表达式支持函数形式（`(field) => ...`）；另有 `x-rules`、`effects`（响应式联动，监听其他字段状态变化，可联动校验规则、加载数据）。计算字段直接用表达式/函数算 `value`。Designable 设计器中的**可视化联动配置面板细节未获取到**（检索只得到 schema 文档与社区学习笔记），但可以确定其模型是"**依赖→效果**"声明式，与字段强绑定。

**可学之处**：① "依赖字段 → 效果状态"的声明式心智模型，天然适配表单字段（比事件更贴近业务语言："当 省份 变化 → 重置 城市"）；② 状态类联动（显隐/禁用/必填/赋值）被显式归类为标准能力；③ 表达式/函数作为统一计算语言，从简单条件到复杂计算平滑升级。

### A3. 钉钉宜搭 —— 字段属性内的"数据联动规则 + 公式字段"（业务化程度最高）

**官方文档（已抓取「数据联动」正文）**。形态：**在字段的属性配置面板里配置联动规则**（不是全局画布、不是弹窗连线）。步骤：选择"数据关联表"（当前应用的其他表单，或跨应用数据集）→ 设置关联条件（"当前表单字段 产品名称 的值 = 被关联表字段 产品名称 的值"）→ 指定回填（"当前字段 数量 显示为被关联表字段 库存数量 的值"）。文档明确"一般用于设置组件的默认值"，并提供**组件类型配对矩阵**（单选↔下拉单选/单行文本/数值、多选↔多选、日期↔日期……地址/关联表单仅支持作为条件规则），把"哪些字段之间能联动"直接约束死，从源头减少配置错误。

- **计算字段**：宜搭有独立"公式函数"模块（公式字段自动计算）。
- **生命周期/脚本兜底**：开发者模式提供 `didMount` 等 JS 钩子，文档示例为 `this.$('textField_vq5mqtb').getProp().onChange()` 手动触发联动（业务侧仍叫"字段 id 点方法"，但藏在开发者区域）。
- 另有"关联选项设置"（下拉选项随另一字段过滤）、"跨应用获取表单数据"。

**可学之处**：① 把联动下沉为**字段属性**而非全局事件，心智负担小；② 规则用"字段级自然语言"（当 X=值时 Y 回填 Z）；③ 组件类型配对矩阵约束可行性；④ 复杂能力（跨表单、JS）分级，默认不打扰业务用户。

### A7. Retool —— 事件处理器列表（事件 → 动作 → 条件），最像"标准答案"的桌面级实现

**官方文档（已抓取「Configure event handlers」部分正文）**。形态：**组件属性面板中，每个交互事件（onClick/onChange…）对应一组 event handlers 列表**；每个 handler = **一个动作 + 可选条件**。动作类型：Run query、Set state variable、**Control component**、Open URL、Navigate to、Run script 等。两个关键细节：

- **Control component 动作**：选择动作后**先下拉选目标组件，系统自动列出该组件可用的方法**（文档原例：table 的 `.setFilter()` 方法被列出供选择）——"组件树 + 手动填方法名"在这里被"目标下拉 + 方法自动枚举"替代，这是对 epic-designer 现状最直接的改进点。
- **Only run when 条件**：每个 handler 可配 `{{ switch1.value }}` 条件，false 时不触发；handler 支持复制/删除/排序。

**可学之处**：事件-动作-条件的轻量三层结构；"选目标→看方法"的强引导；条件内联在 handler 上。

### A8. Appsmith —— 属性面板事件动作绑定 + 全链路表达式

**官方文档（已抓取 update-list-data 片段）**。形态：**widget 属性面板（property pane）中为事件（onClick 等）绑定动作列表**：Show modal、Execute query、Navigate to、Store value 等；目标通过**动作内下拉**选择（选择哪个 modal、哪个 query）；跨组件读值用 `{{ widget.value }}` 表达式；复杂逻辑统一收敛到 **JS Objects**（一个集中写 JS 的面板）。模式本质是"预设动作 + 表达式语言"双轨：简单场景点选，进阶场景写表达式。

### A9. Budibase —— 组件动作步骤 + 自动化流程（细节未获取到）

搜索结果确认其形态为：组件（按钮等）可配置 **Actions 步骤列表**（更新行、导航、通知等），另有独立的 **Automations**（自动化流程编辑器）。**具体动作绑定 UI 细节未获取到**，不编造。

### A10. LowCodeEngine —— EventSetter：事件 → 代码块/方法绑定（最"开发式"，反面教材）

**官方文档（已抓取 EventSetter 页）**。形态：物料（组件）在 `configure.support.events` 中**声明事件名列表**（onChange/onExpand/onVisibleChange 等）；属性面板的 EventSetter **下拉选事件 → 绑定到 schema 中 method 节点或新建事件（默认加 `_new` 后缀）→ 点击确定跳转到对应代码插件/代码块区块**去写逻辑；如需传参，打开"扩展参数设置"在代码面板里编辑。**绑定粒度是"事件→方法/代码"，逻辑本体在代码里**——对开发者高效，对业务用户门槛极高。这正是 epic-designer 当前"开发式弹窗"的上游同类，可作为对照而非学习对象（细节见 D2）。

### A12. form-generator（jakHuang 系）/ FcDesigner（FormCreate 系）—— 字段配置内的 control 规则数组

**CSDN 教程（已抓取片段，FcDesigner/FormCreate）**。形态：**在字段的配置面板里写 `control` 规则数组**：`[{ value: '1', rule: ['field1','field2'], method: 'display' }]`——含义"当本字段值 = '1' 时，控制 field1/field2 的显示/禁用/必填（method: display/disabled/required）"；支持自定义条件函数 `handle: (val, api) => boolean`。**纯规则-列表模式，配置在字段上**，被控字段用字段名（name）引用。对表单设计器来说这是最轻的实现，但只能表达"值→状态"，**表达不了"调用方法/跨组件取数/计算"**。jakHuang 版 form-generator 的联动配置细节未获取到（仅 npm 包命中了搜索），不编造。

搜索结果指向：连线式代表是 Node-RED（Palette + Workspace + Sidebar）与各类流程编排器（OutSystems/Mendix 的逻辑编排对比测评）；社区对 Node-RED 在复杂场景的批评集中在**连线面条化、可维护性差**（"Node-RED 是否适合工业场景"的讨论）。**表单场景几乎没有主流产品把"元素间联动"做成连线图**——连线的表达力用在"流程/自动化"（节点=步骤），而非"表单字段联动"（节点=字段没有控制流语义）。这是 D1 的重要论据。

## C. 可借鉴的最佳实践模式（8 条）

### C1. 事件-动作列表（按事件分组、动作可排序/增删/条件化）

- **模式**：把"元素 A 的 change 事件"作为一个条目，其下挂一组按序执行的动作；每个动作 = 预设动作类型 + 目标 + 参数，可加"仅当…"条件。
- **来源**：amis onEvent、Retool event handlers、Appsmith 属性面板。
- **为什么适合本场景**：epic-designer 底层已是 `on` 属性 + 动作列表（event.vue / AigenActionEditorItem.vue 已验证），**保留骨架、只重做表达层**成本最低、风险最小；事件-动作与"生命周期事件"天然同构（生命周期也是"事件"），统一心智。
- **落地要点**：① 右侧面板按"组件事件组 + 生命周期组"展示（现状已有，保留）；② 每个动作条目展示"图标 + 动作名 + 目标组件label + 方法名"摘要（现状已显示 label+methodName，可加动作类型图标与参数摘要）；③ 支持拖拽排序、复制、删除、**启用/停用开关**、**每动作独立"仅当…"条件**（Retool 的 Only run when）；④ 动作数 >3 时折叠为"查看 N 个动作"。

### C2. "选目标 → 自动列方法"（Control component 模式）

- **模式**：配置动作时，先用**搜索下拉/画布点选**选定目标元素，再展示该元素**可用方法/属性列表**供选择；选择后生成参数表单。
- **来源**：Retool Control component（选组件后自动列出 table.setFilter() 等）、Appsmith 动作目标下拉。
- **为什么适合本场景**：当前动作配置弹窗是"组件树+方法列表"，方法列表对全量组件平铺、与目标组件脱钩，用户要自己知道"哪个组件有哪些方法"。改成"**先选目标，方法列表按目标过滤**"直接把心智负担砍半，且天然防错（只能选目标组件真实存在的方法）。
- **落地要点**：① 目标选择支持两种入口并存——弹窗内搜索下拉 + **画布点选**（点选时高亮目标组件并回填）；② 选中后方法下拉来自该组件 schema/组件配置声明的方法表（如 input.setValue、form.reset 等，需要给组件方法表补声明元数据：方法名+中文名+参数 schema）；③ 参数表单按方法声明自动生成（字段→表单控件映射复用现有 attributeItem 机制）。

### C3. 动作摘要可视 + 画布回显（所见即所得）

- **模式**：绑定关系不只是弹窗里的表单，还要以"可读摘要/徽标"形式呈现在画布与大纲上。
- **来源**：epic-designer 大纲已有"已绑定事件"徽标（outline.vue）；LowCodeEngine 事件徽标；amis 编辑器属性面板。
- **为什么适合本场景**：用户最大的挫败感是"画布上看不出谁绑了谁"。给绑定了事件的组件加角标，点击角标直达该事件编辑；画布上选中组件时右侧面板直接展示其事件。
- **落地要点**：① 大纲树与画布组件角标显示事件数量；② 从角标进入编辑时定位到对应事件条目并高亮；③ 编辑动作的目标组件时，可在画布对目标组件做短暂高亮/描边（动效提示"你绑的是它"）。

### C4. 分层能力模型：快速联动层 → 事件-动作层 → JS 兜底层

- **模式**：同一诉求提供三档入口，默认展示最低门槛的一档，高级能力折叠：①**快速联动规则**（"当 字段X 满足条件 → 隐藏/禁用/必填/赋值/清空 字段Y"）；②**事件-动作**（完整动作编辑器，C1/C2）；③**自定义 JS/公共函数**（折叠在"高级"里）。
- **来源**：宜搭（字段内规则 + 开发者 JS 分级）、amis（动作 + JS 动作 + 逻辑编排分级）、Appsmith（点选 + JS Objects）。
- **为什么适合本场景**：现状只有一档（开发式弹窗），业务用户直接撞墙。增加"快速联动"这一业务层能覆盖最高频诉求（显隐/禁用/必填/赋值），且**可以直接复现为 schema 上的新字段**（如 `linkage` 规则数组，或映射为 on 事件预编译），不破坏现有 `on` 运行时。
- **落地要点**：① 事件面板顶部加"快速联动"Tab（规则列表，类似宜搭字段属性规则）；② 快速联动规则与事件-动作互转（规则 → 自动生成 onChange 动作）；③ 高级/自定义动作统一折叠，入口"更多…"。

### C5. 业务化生命周期命名 + 收敛

- **模式**：生命周期事件用**业务语义命名**（"页面/表单加载完成"、"元素渲染完成"、"值更新后"、"元素销毁前"），并默认只暴露常用的 3-4 个，冷门的折叠。
- **来源**：amis 组件事件表（业务化事件名）；对比对象：epic-designer 现状的 `vnodeMounted`/`vnodeBeforeMount`/`vnodeErrorCaptured`。
- **为什么适合本场景**：这是任务背景点名的痛点——Vue 术语对业务用户是噪音。生命周期在表单场景的常见诉求其实只有：初始化赋值/回填、值变化后联动、清理。
- **落地要点**：① 8 个 vnode 事件映射为业务名（挂载完成→"加载完成"、更新完成→"值更新后"…），`type` 保持不变（运行时零改动），只改展示文案；② 默认展开"加载完成/值更新后"，其余收进"更多生命周期"；③ 文案放组件/平台可配置的映射表，便于国际化。

### C6. 组件事件/方法表由物料声明（事件表 + 方法表元数据）

- **模式**：每个组件的"可监听事件"与"可调用方法"由组件物料声明（名称、中文名、参数 schema），设计器据此自动生成下拉选项与参数表单，而不是硬编码。
- **来源**：LowCodeEngine（`configure.support.events` 声明事件名，EventSetter 据此生成下拉）、amis（各组件文档附事件表）、Retool（组件方法库自动枚举）。
- **为什么适合本场景**：epic-designer 是组件插件化架构（pluginManager.component），事件已有 `config.event` 声明（event.vue 第 72 行读取），**方法表尚未结构化**——补上"方法名+中文名+参数 schema+返回值"声明，就能驱动 C2 的目标选择器与参数表单，也是画布点选方案的地基。
- **落地要点**：① 扩展组件配置声明：`events`（已有）+ 新增 `methods`（含参数定义）；② 事件面板/动作编辑器全部从声明渲染；③ 缺声明的组件回退到"自定义函数"入口，不阻塞。

### C7. 表达式作为统一"值语言"（输入可点选、可手写）

- **模式**：动作参数、条件、赋值都允许填入"表达式/字段引用"；编辑器提供字段变量点选面板（列出当前表单字段、事件数据、公共函数），点选插入表达式，同时允许直接手写。
- **来源**：amis（`${event.data}`、`${__rendererData}` + 编辑器变量提示）、Appsmith（`{{ widget.value }}` + 变量面包屑）、Retool。
- **为什么适合本场景**：跨元素取值（A 的 change → 用 B 的值算 C）是刚需；纯点选能覆盖常用，手写表达式兜底长尾。epic-designer 已有 `getValueByPath`/`find().getVal()` 能力，需要的是**编辑器层的变量面板 + 表达式校验（输入即提示非法引用）**。
- **落地要点**：① 参数输入框旁提供"插入字段/函数"面板（搜索 + 分组：表单字段/事件数据/公共函数）；② 表达式运行时求值失败给明确错误（引用哪个字段不存在）；③ 表达式语法沿用现有 getVal/getValueByPath 能力，避免双语法。

### C8. 调试与预览：动作运行日志 / 联调面板

- **模式**：设计器内置"运行日志"视图，实时打印：哪个事件触发 → 依次执行了哪些动作 → 每个动作的入参与结果；可开关、可筛选组件。
- **来源**：amis（浏览器 console 打印 `run action ajax` + 参数 + 结果，官方文档明确此功能）。
- **为什么适合本场景**：联动/计算"为什么不生效"是设计器最高频售后问题；日志面板让用户自己定位（是事件没触发，还是动作被条件拦了，还是参数引用错了）。
- **落地要点**：① 预览模式下注入 logger（事件/动作/条件/表达式求值各打一条）；② 日志 UI 放底部抽屉或独立 tab，支持按组件过滤；③ 与 C4 的快速联动联动（规则命中与否也打日志）。

## D. 不建议照搬的模式及原因

### D1. 纯连线图（Node-RED 式"字段拖线连字段"）

- **不建议**。原因：① **面条复杂度**——表单 10+ 字段、每字段多个联动时，连线交叉成"意面"，维护与阅读成本随联动数平方级上升（Node-RED 在工业流程场景已被大量吐槽同一问题）；② **语义错位**——连线适合"控制流/数据流"（节点=步骤），表单联动是"事件-响应/依赖-效果"，每个事件对多个动作、每个字段被多个源影响，用连线表达"一因多果、多因一果"非常勉强；③ **子表单/嵌套字段**（epic-designer 支持容器嵌套）在线连图里几乎无法表达层级；④ 实现成本高（连线引擎 + 布局 + 防误触），而收益在表单场景远低于事件-动作列表。**结论：只把"画布点选目标"做成交互入口（C2），不把连线做成主要呈现范式。**

### D2. 纯脚本/代码块绑定（LowCodeEngine EventSetter 式："事件 → 跳到代码面板写逻辑"）

- **不建议作为主路径**。原因：① 业务用户门槛最高——逻辑本体在代码里，点选配置名存实亡；② 代码散落在各组件事件上，难以审查/复用/迁移（对比：Appsmith 收敛到 JS Objects 仍被诟病，LowCodeEngine 索性定位开发者）；③ 与 epic-designer 要服务的"表单设计"用户画像错位。**保留为兜底（C4 第三档），默认折叠。**

### D3. 只有"值→显隐/禁用"的简单规则（FcDesigner control 式），没有升级通道

- **不建议作为唯一能力**。原因：规则数组只能表达"当值=… → 控制状态"，**覆盖不了调用方法、跨组件取数、计算赋值、条件编排**；若产品只有这一档，复杂表单直接劝退（用户会去写代码绕过设计器）。**正确姿势：快速联动规则（C4 第一档）+ 事件-动作（第二档）并存，规则是入口而非天花板。**

### D4. 全局广播滥用（amis 广播机制）

- **不建议把广播作为默认交互**。原因：广播解耦了"一因多果"，但**"谁在监听谁"在 UI 上不可见**，配置端与排查端都容易失控；amis 自己也把它定位为进阶动作。**epic-designer 若引入，仅作为事件-动作的"高级动作"之一，且必须在编辑器中提供"监听关系列表"视图兜底可查性。**

### D5. 完全照抄"组件类型配对矩阵"的硬约束（宜搭）

- **部分不建议**。宜搭用"哪些字段类型之间能联动"的矩阵约束用户，确实降低错误率；但矩阵是**产品级运营决策**，需要长期维护且会误伤合法诉求（如文本字段与数字字段的换算联动）。**落地建议：软约束（配置时给出兼容性提示与黄色警告）而非硬拦截**，避免过度限制。
